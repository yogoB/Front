# A. 개정 방향 (v1)

## A0. 다시 세운 원칙

> 요고비 사용자는 복잡한 통신·구독 구조를 **공부하러** 오는 사람이 아니라, 그것을 **대신 판단해달라고** 오는 사람이다.

좋은 경험은 "많이 입력 → 복잡한 결과 비교 → 내가 선택"이 아니라,
**"몇 가지 답 → 요고비가 내 상황을 정리 → 지금보다 얼마나 좋아지는지 → 가장 적절한 안까지 추천"** 이다.
멘토 지시: **지금은 기능을 추가하지 말고 아래 순서로 정리한다.**

## A1. (1순위) 온보딩 구조 단순화

문제: 입력이 많고 길다. 끝이 언제인지 몰라 실제보다 길게 느껴진다. "복잡함을 대신 정리해준다"는 서비스가 시작부터 긴 설문을 요구하면 문제 정의와 충돌한다. → **질문 수를 줄이기보다 "짧게 느끼게" 만든다.**

- **결과지향 챕터 라벨**: `기본/요금/구독` → "생활 패턴 → 요금 상황 → 구독 정리" 같은 의미 단위. 각 단계에 **"여기까지 하면 예상 절감액을 계산할 수 있어요"** 식 기대 결과를 병기(단순 % 진행률 대체).
- **가치의 점증 노출**: 입력이 쌓일수록 **예상 절감액/정확도가 점점 구체화**되는 형태. 긴 과정을 "진행 경험"으로.
- **묶어서 받기**: 한 화면에서 처리 가능한 정보는 과도하게 잘게 나누지 않는다.
- **리듬**: 일러스트·시각 변화로 단조로움 완화.
- 우리 코드 반영: `light.js`/`detail.js`의 `progress` 라벨·단계 카피 개편, 각 단계 하단에 예상 절감액 미리보기 슬롯 추가.

## A2. (2순위) 결과 화면 전면 재구성

문제: 정보가 동시에 강조돼 무엇을 먼저 볼지 불명확. 사용자는 결국 하나를 알고 싶다 — **"그래서 지금보다 얼마나 좋아지나?"**

- **상대값 우선**: 최상단 히어로 = **절감액**. 절대 총액은 보조. (현재는 총액이 크게, 절감은 작게 → 뒤집는다.)
- **같은 기준 나란히 비교**: 현재 vs 추천을 같은 항목은 같은 행에. 무엇이 없어지고 무엇이 생기는지 즉시 보이게. (애플·삼성·다나와 **제품 비교 UI** 패턴 참고.)
- **요고비가 하나를 추천**: A/B 동일 비중 나열 금지. **"요고비 추천"** 1안을 명확히 밀고, 나머지는 대안(`최대 절감` / `현재 통신사 유지`)으로 보조 표기.
- **시뮬레이터화 (A6과 연결)**: 결과에서 조건을 바로 수정하면 추천·절감액이 즉시 갱신. 리포트가 아니라 시뮬레이터.
- 우리 코드 반영: `results.html`/`results.js` — 절감액 히어로, 추천 1안 강조, 인라인 수정 슬롯.

## A3. (3순위) 입력 방식 개선 — 정확보다 "쉽게 답하게"

- **금액은 구간 우선**: `3만원대 / 4만원대 / 5만원대 / 직접입력`. 정확한 원 단위는 **결과 화면에서 보완**(예: "6만원대" → 나중에 72,320원). *라이트 통신비는 이미 구간 칩으로 반영됨 — 원칙을 전체에 일관 적용.*
- **구독·요금제는 검색 중심**: 전체 목록 나열 → **검색 + 멀티셀렉트** 기본. 인기/최근 선택 서비스는 보조 노출. 없는 서비스는 예외 처리·추가 요청. *현재 라이트 구독은 "검색창 + 전체 나열"이라 나열이 메인 → 검색 우선으로 재배치.*

## A4. (4순위) 자연어 입력 역할 재정의

- 빈 입력창을 앞세우지 않는다. **미리 정의된 추천 문장 칩**을 먼저: "넷플릭스는 꼭 유지하고 싶어요" / "통신사는 바꾸고 싶지 않아요" / "가족결합은 유지하고 싶어요". 자유 입력은 보조.
- 구조화 가능한 정보는 UI로, 개인 조건만 자연어로. *리디자인엔 아직 자연어 화면 없음 → 칩 방식으로 신규 설계(기존 `app.html` 자유 챗봇은 참고만).*

## A5. (5순위) UI 위계 정리

- **모노톤 + 강조 최소화**: 비교 화면은 전체를 차분하게, **추천안·실제 차이값에만** 강조색.
- **브랜드 컬러 남용 금지**: 금융·가격 UI에서 빨강/초록은 상승·하락 의미 → 브랜드 초록을 숫자에 무분별하게 섞지 않는다. *현재 결과의 초록 숫자 강조를 절감액 등 핵심으로 한정.*
- **데스크톱 배치 별도 검토**: 모바일 UI를 그대로 확대하지 않는다.
- **레퍼런스 고정**: 결과 비교 화면은 제품 비교 UI(애플/삼성/다나와)를 기준으로 폰트·여백·컬러·컴포넌트를 제약해 구현.

## A6. 결과 화면 인라인 수정 (2순위에 포함)

온보딩 입력이 대략적이었을 수 있으므로, 결과에서 **현재 상태·추천 조건을 바로 수정 → 즉시 재계산**. 실데이터는 `/recommendations` 재호출. (과거 옵션이던 프론트 재계산 `recommend-mock` 은 삭제됐다 — 되살리려면 프론트가 금액을 만들게 되므로 절대 원칙 2와 충돌한다. A9-② 결정 때 이 점을 본다.)

## A7. 포지셔닝 · 첫 화면 메시지

- **단일 메시지**: "통신요금+구독료 **다이어트 솔루션**". 개인화·라이프스타일은 그 목표의 *방법*으로 둔다. 각인 목표: "일단 요고비에 오면 내가 지금보다 얼마나 줄일 수 있는지 안다."
- **첫 화면 증거**: 평균값 대신 로그인 후 결과를 확인한 이용자의 실제 진단 절감액 표본을 무작위로 순환한다. 표본 출처와 한계는 `!` 툴팁으로 밝히며 식별 정보는 노출하지 않는다.
- **상대적 맥락 카피**: "지금 얼마나 낭비하나요?"(추상) → "20대 직장인은 평균 ○원 더 낸다" 같은 상대 비교. ⚠️ **근거 데이터·출처가 확보되기 전에는 단정 카피 금지** — 구현 가능성·출처는 별도 검토(아래 결정 필요).

## A8. 현재 구현 대비 — 유지 / 변경 / 신규

| 영역 | 유지 (이미 부합) | 변경 | 신규 |
|---|---|---|---|
| 모드 분리 | 라이트/디테일 2수준 진단(피드백 #2와 일치) | 디테일 유도를 "불완전" 아닌 **긍정적 가치**로 문구화 | — |

## A9. 결정 필요 (사인오프)

1. **상대적 맥락 메시지(#10)**: 평균 소비 데이터의 **출처**를 확보할 수 있나? → **2026-09-16 삭제.** 출처를 못 구해 랜딩의 또래 평균 비교를 걷어냈다. 되살리려면 출처부터 확보하고 이 항목을 다시 연다.
2. **결과 실시간 재계산(#7)**: 목업 재계산으로 갈지, 이번에 `/recommendations` 실연동까지 갈지. (BE 팀 협의 대상)
3. **통신비 반영**: 통신비는 현재 추천 계산 **미반영(메모)**. 절감액 기준을 "정가 대비"로 유지할지, 통신비를 실제 반영하려면 BE 변경 제안 필요.
4. **작업 순서**: 멘토 우선순위(온보딩→결과→입력→자연어→UI)대로 갈지 확인.

# B. 화면·BE 매핑 (v0 — 참고 유지)

아래는 Figma 기반 최초 정리다. 화면 인벤토리와 ✅/⚠️/❌ BE 매핑은 여전히 유효하다. 카피·배치·강조는 위 **A(개정 v1)** 를 우선한다.

## 1. 전체 화면 지도

```
랜딩(마케팅)
  └─ [내 요금제 진단받기] → 진입(모드 선택)
                              ├─ 라이트 모드 ─ ①데이터(범위) → ②통신비(범위) → ③구독 → [분석]
                              └─ 디테일 모드 ─ ①통신사+약정 → ②희망요금(범위) → ③희망구독(유지/해지) → [분석]
                                                                                        │
                        (라이트·디테일 공통) 분석 로딩 → 비교 결과표 → 전환 액션 캘린더
로그인/회원가입: 전 구간 선택. (account.html 기존 화면 재사용)
```

> **D-34(2026-09-17): 가입·로그인은 Google 버튼 하나다.** `signup.html`(이름·이메일·비밀번호·확인·닉네임)과
> `login.html` 의 비밀번호·복구 코드 단계, `account.html` 의 계정 연결 폼이 사라진다. 가입 화면은 따로 없다 —
> 가입과 로그인이 같은 버튼이다.
>
> **D-36(2026-09-17): 로그인은 더 이상 전 구간 선택이 아니다.** 결과 리포트는 **로그인해야 보인다.**
> 모드 선택·입력·계산·"모름" 경로까지는 비회원으로 끝까지 가고, 막히는 지점은 **결과 화면 하나**다.
> **미리 알리지 않는다**(사용자 결정 2026-09-17). 입력 전 고지도, 진행 중 예상 절감액 티저도 없다 —
> 로그인 후 결과 화면에서 한 번에 전부 연다. 비로그인 결과 화면은 리포트 대신 "Google 로 계속하기" 하나를
> 그리고 **금액은 한 줄도 비치지 않는다.** 입력값은 유지해 로그인 후 같은 자리에서 이어지게 한다.
> 이 배치의 대가는 "다 하고 나서 막힌다"이고, 그 이탈율이 CBT 가 재려는 값이다.
> 되돌릴 수 있게 **화면 게이트로만** 두었다(API 는 공개).
> 캘린더 담기도 회원 전용이며 이는 정책이지 기술 제약이 아니다(`BE_main/docs/calendar-integration-findings.md`).
>
> **시안 반영(2026-09-17): 시안 5장 반영(모드 선택·라이트 1/2단계·로그인·캘린더).** 브랜드색은 민트 토큰으로 교체.
> 시안과 다르게 둔 것 — 로그인의 이메일 입력·Sign in 은 넣지 않는다(D-34, BE 에 없음). 라이트 2단계 통신비는
> 시안의 단일 입력 대신 구간 칩 + 직접입력 유지(A3). 데이터 슬라이더는 구간 단일 핸들(양쪽 핸들은 모델 변경이라 보류).
> 캘린더 "Google 캘린더 연동하기"는 링크 방식 그대로라 "담기"로 적는다. 주간 보기는 시안대로 뺐다.
>
> **캘린더 고도화(2026-09-18, 시안 2차):** 머리판의 현재→전환 금액 띠를 빼고 실행 시점 칩(서버 판정) + 연동 버튼으로.
> 격자는 표 선·이웃 달 날짜·TODAY 배지·단계색 테두리, 일정마다 Google 일정 추가 링크(↗). 왼쪽에 "실행 상세 및 가이드"
> 아코디언(`<details>`, 금액 없는 절차 안내만). 맨 아래 "확인하고 진행하기"는 담기 패널을 여는 같은 동작이다.
>
> **D-36 개정(2026-09-18, 사용자 결정 + 시안): 게이트에 절감액 티저 한 줄을 넣는다.**
> D-36 이 "이탈이 높게 나왔을 때 꺼낼 카드"로 남겨 두었던 티저를 꺼냈다. 비회원도 **계산까지 간다** —
> 로딩이 끝나면 리포트를 흐린 뒤 검은 모달에 "고객님의 분석이 끝났어요 / 최대 ○○원 절감 받을 수 있네요 /
> 구체적인 내용과 일정플랜이 궁금하신가요?" + 로그인 버튼을 띄운다. 절감액이 0 이면 그 줄을 적지 않고,
> 금액에는 기준(지금 요금제보다·정가 대비)을 함께 적는다(절대 원칙 4).
> 그대로 둔 것 — 입력 전 고지 없음, 막는 지점은 결과 화면 하나, **화면 게이트일 뿐 API 는 공개**다.
> `<dialog>.showModal()` 이 뒤 화면을 inert 로 만들어 탭으로도 닿지 않고, ESC 로는 닫히지 않는다(게이트니까).
> 나갈 길은 '조건 다시 고르기' 하나를 남겼다 — 막다른 길을 만들지 않는다.
> 캘린더 게이트는 종전 그대로(전체 화면 GuestGate)다 — 캘린더에는 먼저 보여줄 절감액이 없다.

- 라이트 결과의 "더 정확한 절감받기"는 **디테일 모드로 유도**하는 링크다.
- 결과 화면은 라이트·디테일 **동일**하다.

## 2. 화면별 상세 + 백엔드 매핑

범례: ✅ 현재 BE로 됨 · ⚠️ 변환/매핑 필요 · ❌ 현재 BE에 없음(작업 또는 목업 필요)

### S0. 랜딩 (신규)
헤더(로고+로그인), 히어로(헤드라인·CTA·폰목업), 지표 4칸, "이렇게 작동해요" 4스텝, 푸터.
→ **BE 무관.** 정적 마케팅 페이지. 지표 수치(1,200+/50+/₩34,000/96%)는 **고정 문구**인지 실데이터인지 확인 필요.

### S1. 진입 · 모드 선택 (신규)
검정 pill 3개로 "데이터사용량·통신비·구독서비스 입력하고 분석합니다."를 한 줄 안내하고,
바로 아래 카드 2개(라이트/디테일)로 분기한다. 배경은 진단 화면과 같은 밝은 회색이다.
→ **BE 무관.** 선택에 따라 다른 입력 플로우로 분기.

### 라이트 L1. 데이터 (범위 슬라이더)
"한 달에 데이터 얼마나 쓰세요?" 5~15GB 슬라이더 + "모르겠어요 건너뛸게요".
→ `monthlyDataGb`(정수 필수). **⚠️ 범위→대표 정수 변환 필요. ❌ 건너뛰면 BE 필수값이 빔.**

### 라이트 L2. 통신비 (범위 칩)
"실제로 내는 금액?" 칩(3만↓/3~5만/5~7만/7만↑/직접입력) + 건너뛰기.
→ **⚠️ 통신비는 현재 추천 계산에 미반영(메모).** 입력받아도 절감 기준은 "정가". 실제 반영하려면 BE 변경.

### 라이트 L3. 구독
검색 + 서비스 체크박스 + 등급 드롭다운. 좌측 현재 예상 지출 카드. `분석 시작하기`.
→ `wantedServiceIds` ✅ / 등급 `tierIds`는 `/calculator`용 ✅ / 카탈로그는 `GET /catalog/services` ✅.

### 디테일 D1. 통신사 + 약정
통신사 검색(SKT/KT/LGU+ + **알뜰폰 브랜드: 세븐모바일/M모바일/헬로모바일/스노우맨…**) → "약정 남았나요?" Y/N → Y면 **위약금 경고 + 약정 종료일(date)**.
→ `currentCarrier` ✅(3사) / **⚠️ MVNO 개별 브랜드는 BE enum에 없음**(알뜰폰 하나로 통합 or BE 확장) / 약정여부→`contractType` ⚠️ 부분 / **약정 종료일·위약금 ❌ BE 미계산(메모)**.

### 디테일 D2. 희망 요금
"희망하는 지출요금" 데이터 범위 슬라이더(5~15GB).
→ `monthlyDataGb` ⚠️ 범위 변환. (L1과 동일 이슈)

### 디테일 D3. 희망 구독 (유지/해지)
서비스별 **유지/해지 드롭다운** + `추가하기` 모달(티빙/웨이브/쿠팡/애플TV+/멜론/스포티파이…).
→ `wantedServiceIds` ✅ / **⚠️ "유지/해지" 구분은 BE에 없음**(현재는 "추천 포함" 여부만. 기존에 필수/대체/불필요를 이 이유로 단순화했음).

### R0. 분석 로딩 (공통)
"최적 요금 조합 탐색 중" + 체크리스트(DB조회→결합분석→번들할인→개인화계산→완료).
→ 실제로는 `POST /recommendations` 한 번의 응답 대기. **체크리스트는 연출**(각 단계별 실제 진행 신호는 BE에 없음).

### R1. 비교 결과표 (공통) — **가장 큰 갭**
3열: `현재 상황 ₩82,000` / `추천·최적값 🌟 BEST ₩73,900` / `최저 요금제 기준 ₩94,800→₩73,900`.
행: 요금제/월요금/데이터/**통화/부가혜택/할인·적립/약정기간/위약금**. 상단 `1·6·12개월` 탭. 하단 "왜 나에게 추천됐나".
→ 매핑:
- 추천 목록/총액/절감/출처: `POST /recommendations` ✅ (단, 응답은 결과 N개 리스트지 "현재/추천/최저" 3열 프레이밍이 아님 → **⚠️ 프론트가 재구성**).
- "현재 상황" 금액: 통신비가 메모라 **⚠️ 사용자 입력 기반**.
- **통화/약정기간/위약금 행: ❌** BE breakdown은 항목·금액·출처 구조지 Calls/Contract/Penalty가 아님.
- 부가혜택: `GET /plans/{id}/benefits` ✅ 부분.
- 1/6/12개월 탭: 월 금액 ×6, ×12 표시 ⚠️(단순 표시 곱셈, 금액 "계산" 아님으로 처리).
- "왜 나에게 추천됐나"(AI 설명): **❌** 프론트는 AI 서버 직접 연결 안 함(챗봇 엔드포인트만 존재).

### R2. 전환 액션 캘린더 (공통) — **전면 신규**
현재→전환 금액, 단계별 가이드(준비→가입→구독정리→완료), 월간 캘린더+이벤트, `Google 캘린더 연동`.
→ **❌ 대응 BE API 전무.** 위약금·전환 시점 최적화는 명시적 미지원. Google Calendar 연동은 완전 신규 기능(OAuth·이벤트 생성).

## 4. 사인오프가 필요한 결정

BE 계약을 바꿔야 하는 항목은 **팀/BE에 먼저 제안·승인**이 필요하다(작업 루트 규칙). 아래를 정해야 구현을 시작한다.

1. **범위 입력 변환:** 데이터/통신비 범위를 서버에 어떤 정수로 보낼지 (예: 구간 중앙값? 하한? BE에 범위 필드 신설?).
2. **건너뛰기 처리:** 필수값(데이터, 구독≥1)을 건너뛰면 기본 구간 사용 vs 진행 차단 중 무엇?
3. **통신비:** 입력만 받고 참고 표시 vs 절감 기준으로 실제 반영(→BE 변경)?
4. **MVNO 브랜드:** 알뜰폰 하나로 통합 vs BE에 브랜드 목록 추가?
5. **약정/위약금:** 화면에 표시만(목업) vs 실계산(BE 신규)?
6. **결과 3열 + 통화/약정/위약금 행:** 현재 응답으로 채울 수 있는 것만 실데이터, 나머지는 숨김/목업?
7. **AI 추천 사유:** 범위 제외 vs 챗봇/설명 API 신설?
8. **전환 캘린더 + Google Calendar:** 이번 범위 포함 여부. 포함 시 별도 BE·OAuth 작업 필요.
9. **유지/해지:** 서비스별 구분을 실제로 반영할지(BE엔 현재 없음).
10. **브랜딩:** 헤더가 프레임마다 `YogoB`/`요고비교`로 다름 — 하나로 통일.

## 5. 구현 순서 제안

BE 의존이 없는 것부터 화면을 세우고, 실데이터는 되는 지점부터 연결한다. (화면당 커밋 → sub/sh 푸시 → fly 배포로 확인)

1. 랜딩 → 모드 선택 (BE 무관, 리스크 최소)
2. 라이트 입력 3단계 (범위 변환·건너뛰기 규칙 확정 후)
3. 디테일 입력 3단계
4. 분석 로딩 + 결과표(현재 BE로 채울 수 있는 범위)
5. BE 갭 항목(위약금/캘린더/AI 사유)은 결정에 따라 목업 또는 BE 연동 후
